# WeKnora 调研与「智能知识库」设计映射

> 状态：**待确认**（调研完成，供评审）
> 调研对象：腾讯开源 **WeKnora**（v0.9.0，MIT License）
> 目的：为「智能应用 / 智能知识库」确定功能边界、模块划分与交互基线；当前原型以「智能诊断」为 1:1 基线，本文给出改造依据
> 结论先行：WeKnora 是**文档知识库 + RAG 问答**的一体化平台，而不是"知识库管理后台"；它的信息架构是「知识库（KB）→ 文档（Knowledge）→ 分块（Chunk）」三级，配合**独立 FAQ 库 / Wiki 库**两条旁路，以及一条可观测的 **RAG 编排链路**

## 1. 调研范围与结论摘要

### 1.1 调研范围

| 范围 | 内容 |
|------|------|
| 产品能力 | 知识库管理、文档解析、分块、索引、检索、FAQ、Wiki、知识图谱、对话问答、评估、平台管理 |
| 技术实现 | 分块器（策略链 + 校验器 + 画像器）、混合检索（向量/关键词/RRF/重排/MMR）、RAG 编排（阶段化 Pipeline）、多向量库驱动、多租户权限 |
| 文档来源 | 官方文档站 16 个章节（架构、知识库、解析、分块、检索、模型、知识图谱、数据源、Wiki、评估、FAQ、对话体验、平台管理、租户与权限） |

### 1.2 一句话结论

**WeKnora 把"知识库"定义为一套「可配置的入库流水线 + 可配置的检索流水线」，围绕它长出问答、Wiki、FAQ、图谱四种消费形态。** 对原型的直接含义是：智能知识库的主体不是"文件列表"，而是**知识库详情页里的五个配置面**——分块、索引、模型、检索、消费形态。

### 1.3 与我们最相关的 9 个设计判断

| # | WeKnora 的做法 | 对智能知识库的启示 |
|---|---------------|-------------------|
| 1 | 建库时**先选向量库**，`VectorStoreID` 创建后不可改 | 建库向导必须把"检索引擎"作为第一步显式选择，并提示不可逆 |
| 2 | 配置**三级覆盖**：单次上传 > 知识库 > 空间默认 | 参数面板要区分"库级默认"与"本次上传覆盖" |
| 3 | 分块不是"一刀切参数"，而是**策略链（auto/heading/heuristic/legacy）+ 校验器兜底** | 原型不要暴露 5 个算法名给普通用户，用"自动 / 按标题 / 按语义段落 / 固定长度"四档 + 高级参数 |
| 4 | 混合检索的融合在**上层 RRF**，向量库只负责单路召回 | 检索测试页要能分别看"向量命中 / 关键词命中 / 融合后 / 重排后"四列 |
| 5 | 重排是**复合分**（模型 0.6 + 基础分 0.3 + 来源权重 0.1） | 结果卡片要展示分数构成，否则用户无法解释"为什么这条排第一" |
| 6 | FAQ 是**独立库类型**，不是文档里的问答对 | FAQ 独立一级入口，支持 Excel 导入 + 相似问/反例问 |
| 7 | Wiki 是**从文档生成的 Markdown 页面树**，带版本与回滚 | 可作为"知识沉淀"模块，但必须标注"AI 生成、可编辑、可回滚" |
| 8 | 对话链路是**阶段化可观测**的（解析/检索/工具/生成），支持中途追加指令 | 问答区要有"处理阶段"时间线，而不是一个转圈 |
| 9 | 引用可**点击回到原文位置并高亮**（PDF 页码 + 段落框，扫描件走 OCR） | 引用面板是知识库问答的信任基础，必须做 |

## 2. 产品定位与技术栈

### 2.1 定位

WeKnora 面向"把企业文档变成可问答的知识资产"。核心链路：

```
上传 / 导入  →  解析（Parser）  →  分块（Chunker）  →  索引（Embedding + 关键词 + 可选图谱）
                                                              ↓
用户提问  →  查询理解  →  混合召回  →  融合 RRF  →  重排  →  组装上下文  →  LLM 生成  →  引用回链
```

三条旁路：
- **FAQ 库**：不走向量分块主链路，以"标准问 + 相似问 + 反例问 + 答案"为检索单元；
- **Wiki 库**：从文档自动生成结构化 Markdown 页面，形成可浏览的知识树；
- **知识图谱**：入库时抽取实体/关系，检索时补充关系上下文（依赖 Neo4j + APOC）。

### 2.2 技术栈

| 层 | 选型 |
|----|------|
| 后端 | Go（`internal/` 分层：`types` / `application` / `infrastructure`） |
| 前端 | Vue 3 + TypeScript |
| 向量/关键词 | PostgreSQL + pgvector（halfvec + HNSW）+ pg_search（BM25，ParadeDB），默认驱动；另支持 SQLite、Elasticsearch 7/8、OpenSearch、Qdrant、Milvus、Weaviate、Doris、腾讯 VectorDB |
| 图数据库 | Neo4j + APOC（`NEO4J_ENABLE` 为唯一全局开关） |
| 对象存储 | local / MinIO / COS / TOS / S3 / OSS / KS3 / OBS |
| 文档解析 | 内置解析器 + MinerU / PaddleOCR-VL（扫描件）、VLM 图片理解、ASR 音视频转写 |

### 2.3 版本与许可

- v0.9.0，MIT，可直接参考实现细节；
- 迭代重点：分块策略链（v0.9 引入 heading/heuristic 与校验器）、Wiki、FAQ 导入、多向量库驱动、评估。

## 3. 信息架构（页面清单）

WeKnora 的前端是"左侧工作区导航 + 知识库内页签"结构：

```
工作空间
├── 知识库列表（卡片/表格，含类型、文档数、存储、共享范围）
│   └── 知识库详情
│       ├── 文档（列表 / 文件夹树 / 画廊 / 上传任务面板）
│       │   └── 文档详情（解析时间线 / 分块列表 / 分块编辑与版本历史 / 自定义元数据）
│       ├── FAQ（问答对列表 / 导入导出 / 分类标签）
│       ├── Wiki（页面树 / 页面正文 / 版本与回滚 / 图谱视图）
│       ├── 知识图谱（实体 / 关系 / 抽取结果）
│       ├── 检索测试（召回调试）
│       ├── 评估（数据集 / 指标）
│       └── 设置（分块 / 索引策略 / 模型 / 共享与权限 / 活动 / 用量）
├── 对话（会话列表 / 消息 / 引用面板 / 附件 / 追问建议）
├── 数据源（外部同步）
├── 模型管理（LLM / Embedding / Rerank / VLM / ASR / 存储）
├── 评估中心
└── 平台管理（租户 / 用户 / 配额 / 审计）
```

> 对原型的判断：这是"平台型"信息架构，**入口过多**。我们的单入口方案应把它压缩为**一个知识库 + 顶部模块切换**，把"数据源/模型/平台管理"降级为设置项，把"对话"作为常驻侧栏或独立 Tab。

## 4. 知识库创建与配置分层

### 4.1 三种库类型

| 类型 | 常量 | 用途 | 检索单元 |
|------|------|------|---------|
| 文档库 | `document` | 通用资料（PDF/Word/PPT/Markdown/网页/音视频） | Chunk（分块） |
| FAQ 库 | `faq` | 标准问答、客服话术 | 问答对（标准问 + 相似问） |
| Wiki 库 | `wiki` | 由文档生成的结构化知识页 | Wiki Page |

关键约束：
- `VectorStoreID` 使用 GORM `<-:create` 标签，**创建后不可修改**——建库前必须选好检索引擎，切换引擎只能重建 + 重索引；
- 更新 KB 时会**清除与类型不匹配的配置**（例如非 FAQ 库的 `FAQConfig`）；
- 删除知识库级联删除文档、分块、Wiki 页面与版本。

### 4.2 配置三级覆盖

```
单次上传的处理选项  >  知识库配置  >  空间（租户）默认值
```

- 上传确认页可设置标签、是否生成摘要（**默认开启**）、解析引擎等；
- 分块参数是**库级配置**，修改后**已有文档必须重新解析**才生效；
- 空间级提供默认模型、默认分块参数、默认检索参数。

### 4.3 建库向导（WeKnora 实际步骤）

1. 选择内容类型（文档 / FAQ / Wiki）
2. 选择向量存储（不可逆）
3. 选择 Embedding 模型（需与该库类型匹配，FAQ 库也走向量）
4. 配置分块参数（可先用默认）
5. 配置索引策略（向量 / 关键词 / Wiki / 图谱 四个开关）
6. 上传资料

## 5. 文档解析

### 5.1 解析引擎

- 内置解析器覆盖 PDF、DOCX、PPTX、XLSX、Markdown、HTML、TXT、图片、音视频；
- **扫描件 / 图片型 PDF** 走 MinerU 或 PaddleOCR-VL（`parser_engine_rules` 可按文件类型指定引擎，`xlsx_first_row_as_header` 控制表头）；
- 图片进入 **VLM** 生成描述（`ImageProcessingConfig`，管线 `default` / `smartocr`；`DecideOCR` 在 `contain.text == block` 或 `contain.data_visual == true` 时触发 OCR；`on_unobserved` 默认 true 表示未观测到的图片也处理）；
- 音视频走 **ASR** 转写后再分块；
- 表格有专门的 `table_summary` / `table_column` 分块类型，并可注入 `table_metadata_instructions` 让模型按业务口径生成表元数据。

### 5.2 解析状态与可观测性

当前代码（`internal/types/knowledge.go`）的解析状态不是简单的四态，而是**持久化基础状态 + 派生展示状态**两层：

| 层 | 状态 | 说明 |
|----|------|------|
| 持久化 `parse_status` | `pending` | 已入库、尚未开始解析 |
| | `processing` | 解析管线执行中 |
| | `finalizing` | 主解析已完成，摘要 / 推荐问题 / 图谱等富化仍在进行 |
| | `completed` | 解析与富化全部完成 |
| | `failed` | 解析失败 |
| | `cancelled` | 用户取消 |
| | `deleting` | 删除中，属于过渡态 |
| 派生展示 | `queued` | 仍在队列、长时间未开始，展示"排队中" |
| | `stalled` | 超过阈值（默认约 20 分钟）无进展，展示"疑似卡住"，错误码 `TASK_STALLED` |

补充事实：

- `pending` 与 `processing` 在中文界面通常都显示为「解析中」，但内部阶段不同；`finalizing` 对应「优化中」，若摘要仍未完成则显示「生成摘要中…」。
- 解析与富化是两个独立维度：`summary_status` 另有 `none / pending / processing / completed / failed`，`finalizing` 只表示主解析完成、富化未完成。
- 解析管线阶段为 `docreader → chunking → embedding → multimodal → postprocess`，失败时会记录失败阶段，前端时间线可按阶段展示耗时与原因。
- **`finalizing` 期间文档已经可以被检索**，这是最容易被忽略、但对产品语义最关键的一点。
- 支持取消解析（`cancelled`）；文档另有 `enable_status` 控制是否参与检索，草稿类手工知识不在本文讨论范围。
- 上传任务面板：最多 **3 个并发传输**，显示已传字节 / 剩余时间 / 可检索 / 处理中 / 失败 / 已存在，支持单文件取消与重试，离开页面后后台继续。

### 5.3 上传文件与文件夹的限制

WeKnora 的约束分散在前端、Nginx、Go 服务与 DocReader 四层，核心结论是**按单文件限制，不限制单批文件数**：

| 维度 | 实际限制 | 说明 |
|------|----------|------|
| 单文件大小 | 默认 **50 MiB**，部署期可调 | `MAX_FILE_SIZE_MB` 同时约束浏览器校验、Nginx 请求体、Go 上传处理与 DocReader gRPC；Nginx 实际放宽到 51M 以容纳 multipart 开销。改大需同时重启 app / frontend / docreader，运行中改不生效。 |
| 单批文件数 | **无硬上限** | 每个文件单独发一次请求，不存在"整批请求体"上限；上传队列最多 3 个并发传输，其余排队。 |
| 单批总大小 | **无硬上限** | 只受单文件大小与租户存储配额约束（默认 10 GiB）。 |
| 支持格式 | 以当前可用解析引擎为准 | 前端默认白名单含 PDF、Word、PPT、Excel、EPUB、XMind、TXT、MD、HTML、MHTML、CSV、JPG/PNG、MP3/WAV/M4A/FLAC/OGG；实际 `accept` 会按引擎可用性动态收窄或扩展。 |
| 视频 | **主动排除** | MP4 / MOV / AVI / MKV / WebM / WMV / FLV 即使用户选中也会被过滤，并提示"暂不支持视频上传"。 |
| 文件夹 | 保留目录树，隐藏项跳过 | 任一路径段以 `.` 开头的文件（如 `.git`、`.DS_Store`）不会上传。 |
| 文件夹深度 | 最多 **16 层** | 超出部分被截断，而不是整批失败。 |
| 单级目录名 | 最多 **128 字节** | 按 UTF-8 字节截断并回退到完整字符，中文约 42 字。 |
| 完整目录路径 | 最多 **1024 字节** | 超长时从末尾丢弃层级，直到落入预算。 |
| 目录名清洗 | 去首尾空格、去尾部 `.`、丢弃 `.` / `..`、反斜杠转 `/` | 保证 `a.` 与 `a` 不会变成两个视觉相同的目录。 |
| 重复文件 | 同一知识库内按 **文件内容哈希 + 文件类型** 判重 | 命中返回 409 `duplicate_file`，任务面板计为"已存在"；失败 / 删除中的文档不参与判重。 |
| 空文件夹 | 不保留 | 目录由文件路径反推，没有任何文件的空目录不会出现在文件夹树。 |

产品含义：50 MiB 是 WeKnora 的默认值而非产品常量；真正需要产品决策的是"我们允许多大"以及"超限时如何反馈"。WeKnora 选择**单文件失败、其余继续**，并用右下角任务面板汇总"已存在 / 失败 / 可检索"，而不是让整批上传失败。

### 5.4 对原型的启示

- 文档列表不能只做「解析中 / 已解析 / 失败」。至少要区分**排队中（不可检索）→ 解析中（不可检索）→ 优化中（已可检索）→ 已解析**；否则用户会误以为"还在解析就不能搜"。
- 失败态要能说明**卡在哪个阶段、为什么失败**，并允许重试；完整解析时间线对排障有价值，但原型阶段可以用一行"阶段 + 原因"替代，不必复刻全量 Timeline。
- `疑似卡住`、`取消解析`、`删除中`、文档级启停属于运行时与运维能力，原型可暂不做，但文档设计里要明确它们是**有意裁剪**，不是遗漏。
- 上传不是一次性弹窗而是**可离开的任务过程**，至少要让用户看到排队 / 解析 / 可检索的阶段变化。

### 5.5 横向对照：RAGFlow 的上传与文档列表

RAGFlow 在同一个「上传文件」流程里同时提供「文件 / 文件夹」两个 Tab，选定后进入待上传清单，再点「保存」才真正入库；列表则用高密度表格承载启停、分块数、元数据与解析状态。它的限制按部署形态分两套：

| 维度 | 本地部署 | 云端 SaaS |
|------|---------|-----------|
| 单次总大小 | 1 GB | 10 MB |
| 单批文件数 | ≤ 32 | — |
| 单文件大小 | — | ≤ 10 MB |
| 账号文件总量 | 不限 | ≤ 128 个 |

**值得借鉴**

1. **限制前置**：在投放区直接写清单文件 / 单批 / 总量上限，而不是等上传失败才报错。
2. **拖拽投放**：上传区是一个明确的拖放目标，减少一次“点按钮找目录”的操作。
3. **批量清单**：选完文件先聚合展示，允许移除单个文件后再提交，避免误选后整批重来。
4. **列表承载状态而非只承载文件**：`分块数`、`解析`、`启用` 与文件名同行展示，用户不用进详情就能判断“能不能用”。

**不照搬**

- **硬性 32 个 / 1 GB 上限**：这是云端资源约束的产物，整目录导入会被直接截断。我们改为单文件 100MB 硬限制 + 单次 50 个软提示，超限只提示不阻断。
- **「保存」二次确认**：多一次确认并没有降低误操作成本，反而把上传切成两段。我们保留选完即入库 + 常驻任务中心。
- **「创建时解析」开关**：一旦允许“只上传不解析”，就必须新增一种长期存在的未解析状态，并解释它能否被检索。我们的库设置已经统一了切分与富化，默认自动解析即可。
- **元数据列 / 解析器列**：元数据一期没有承接页面，解析器是库级配置而非文档属性，展示出来只会制造“每篇文档配置不同”的误解。
- **黑色主题**：属于品牌皮肤差异，与信息架构无关。

结论：借它的**限制透明、拖拽入口、批量预检、列表自解释**，不借它的**两段式提交与云端硬上限**。

## 6. 分块机制（最值得借鉴的部分）

### 6.1 参数默认值（`internal/types/knowledgebase.go`、`chunker/splitter.go`）

| 参数 | 默认 | 说明 |
|------|------|------|
| `chunk_size` | **512** 字符 | 约 100–130 英文 token / 约 300 中文 token |
| `chunk_overlap` | **80** | 约 15%，上限被钳制为 `chunk_size / 2` |
| `separators` | `["\n\n", "\n", "。"]` | 段落 → 行 → 句 |
| `strategy` | 空（= `legacy`） | `auto` / `heading` / `heuristic` / `recursive` / `legacy` |
| `token_limit` | 0（不限） | >0 时按语言比例换算字符预算：en 4.0 / de 4.5 / zh 1.7 / mixed 3.0，再 ×0.9 安全系数，与 `chunk_size` 取小 |
| `enable_parent_child` | false | 父块 4096 / 子块 384，子块重叠 = 子块/5 ≈ 20% |
| `languages` | 自动检测 | 语言提示，影响 token 换算与分词 |

> 历史默认 overlap 曾是 64 / 50 / 100，v0.9 统一为 80。

### 6.2 策略链与兜底

```
auto      → 画像器从 [heading, heuristic, legacy] 中选一个子序列
heading   → [heading, legacy]
heuristic → [heuristic, legacy]
recursive → [legacy]
legacy/"" → [legacy]
```

**每一层的输出都要过 `Validator`，不通过则降级到下一层；`legacy` 永不返回空。**

校验器拒绝的典型情况：

| 拒绝原因 | 判定 |
|---------|------|
| `no chunks produced` | 切不出任何块 |
| `single chunk for large document` | 文档 > 2×chunk_size 却只切出 1 块 |
| `too many tiny chunks` | 非尾部 <50 字符的块数量 > 总数 1/4 且 >2 |
| `all chunks far below target size` | 最大块 < chunk_size / 4 |
| `chunk exceeds 2x target size` | 存在超过 2× 目标尺寸的块 |

### 6.3 画像器（Profiler）

| 判定 | 选择 | 条件 |
|------|------|------|
| 结构清晰 | `heading` 链 | `MdHeadingTotal >= 3` 且 `HeadingDensity() > 0.005` 且 `DominantHeadingLevel() > 0` |
| 有视觉/章节边界 | `heuristic` 链 | `HeuristicMarkerTotal() >= 5` 或存在换页符或章节标记 |
| 其余 | `legacy` | 递归字符切分 |

`DominantHeadingLevel()` = 出现 ≥3 次的最浅标题层级。

### 6.4 heading 切分

- 按 Markdown 标题层级切分，**面包屑写入 `ContextHeader` 而非 `Content`**（保证召回文本干净、层级不重复计分）；
- `coalesceTinyChunks` 合并相邻小块的**共享标题前缀**；
- 不变式：`End - Start == utf8.RuneCountInString(Content)`（位置可回链到原文）。

### 6.5 heuristic 切分

边界优先级（高→低）：

| 优先级 | 边界 |
|-------|------|
| 100 | 换页符 `\f` |
| 90 | 编号章节 |
| 85 | 章节标记（中/英/德） |
| 70 | 全大写短行 |
| 60 | 视觉分隔线 |
| 50 | 页脚 |
| 40 | 连续 ≥3 空行 |

- 丢弃落在**受保护区间**（表格 / 代码块 / 公式）内的边界；
- 贪心装箱；
- overlap 先吸附到语义边界，再退化为换行。

### 6.6 推荐参数组合

| 场景 | 策略 | chunk_size / overlap |
|------|------|---------------------|
| 通用文档 | `auto` | 512 / 80 |
| 结构化技术文档 | `auto`（命中 heading） | 512–1024 / 80 |
| OCR PDF / 纯文本书籍 | `auto`（命中 heuristic） | 512–1024 / 80–150 |
| 长篇叙述 | 固定长度 | 1000–2000 / 150–200 |
| 精确检索 | 父子上文 | 父 4096 / 子 384 |
| FAQ | 每条一问一答 | overlap = 0 |

### 6.7 调试能力

`POST /api/v1/chunker/preview`：**不落库**预览切分结果，用于上传前验证参数。原型里的"分块预览"应照此设计——右侧滑出预览，实时显示块数、平均长度、超长/过碎告警。

### 6.8 对原型的启示

1. 分块参数**不要直接暴露 5 个算法名**。建议四档：
   - **自动（推荐）**：按文档结构自动选择
   - **按标题层级**：适合手册、规范
   - **按语义段落**：适合 OCR、书籍
   - **固定长度**：适合无结构长文
2. 参数区只保留三个主项：**块大小 / 重叠 / 分隔符**，其余进"高级"；
3. 必须提供**分块预览 + 质量提示**（"检测到 38% 的块过短，建议增大块大小"）；
4. 改参数后要显式提示"**需重新解析已有文档**"，并提供一键重解析。

## 7. 索引策略

`IndexingStrategy` 四个开关，默认：`VectorEnabled = true`、`KeywordEnabled = true`、`WikiEnabled = false`、`GraphEnabled = false`。

- `NeedsChunks()`：任一开关开启即需要分块；
- `NeedsEmbedding()`：`vector || keyword` 为真才跑向量化；否则**分块只写库、跳过 Embedding 阶段**（`skipStage(StageEmbedding)`）；
- 图谱额外要求 `NEO4J_ENABLE` 全局开关 + 库级 `graph_enabled` 双层门禁。

> 原型：索引策略用四个开关 + 一句人话解释（"向量：语义相似；关键词：术语精确匹配；图谱：实体关系"），并说明"关闭全部索引后仅支持原文浏览"。

## 9. 混合检索

### 9.1 架构：融合在上层

```
                    ┌── 向量召回（Embedding + ANN）──┐
Query ── 查询理解 ──┤                                ├── RRF 融合 ── 重排 ── MMR ── 截断
                    └── 关键词召回（BM25 / FTS）─────┘
```

**关键点：向量库只需支持单模式召回，混合与融合由应用层 `knowledgebase_search_fusion.go` 完成。** 因此换向量库不改变融合语义。

驱动矩阵（`RETRIEVE_DRIVER` 逗号分隔：写广播、读按类型路由）：

| 驱动 | 向量 | 关键词 | 备注 |
|------|------|--------|------|
| `postgres`（默认） | pgvector halfvec + HNSW | pg_search BM25（ParadeDB） | 图片检索也走 ParadeDB |
| `sqlite` | sqlite-vec | FTS5 contentless + 应用层 bigram | 轻量单机 |
| `elasticsearch_v8` | ✓ | ✓ | |
| `elasticsearch_v7` | ✓ | 仅关键词 | 向量能力受限 |
| `opensearch` / `qdrant` / `milvus` / `weaviate` / `doris` / `tencent_vectordb` | ✓ | 视驱动 | |

多存储检索超时：`MULTI_STORE_RETRIEVE_TIMEOUT_SEC`（默认 30s）。

### 9.2 RRF 融合公式

```
rrf   = vectorWeight / (rrfK + vectorRank) + keywordWeight / (rrfK + keywordRank)
score = rrf / ((vectorWeight + keywordWeight) / (rrfK + 1))      // 归一到 [0,1]
```

- 默认权重 **0.7 / 0.3**（向量 / 关键词）；
- 排名按**各自结果列表**从 1 开始；同一块保留其最优排名；
- 单路命中时跳过 RRF，改用 `deduplicateByScore`；仅关键词时按该列表自身最大值归一；
- `rrfK` 与权重来自租户 `RetrievalConfig`（`GetEffectiveRRFK` / `GetEffectiveRRFWeights`）。

### 9.3 重排与合并

- `CHUNK_RERANK` 复合分：

```
final = 0.6 * rerankModelScore + 0.3 * baseScore + 0.1 * sourceWeight
sourceWeight: web_search = 0.95，其余 = 1.0
final = clamp(final, 0, 1)
```

- 阈值过滤 + **top1 兜底**：`rerankFallbackMinScore = 0.15`（用户显式锁定标签/文档范围时降为 0）；
- 无结果且阈值 > 0.3 时，**自动以 `threshold × 0.7`（下限 0.3）重试一次**；
- **MMR 去冗余**：`mmr = 0.7 × relevance − 0.3 × max_jaccard`；
- 重排前对 passage 做**清洗**（剥离 Markdown 结构符），避免格式干扰打分；
- 图片命中可由视觉重排模型打分（jina-reranker-m0、llama-nemotron-rerank-vl-1b-v2）；
- `FILTER_TOP_K`：按分数降序 + 稳定 tiebreak（KnowledgeID / ChunkType / ChunkIndex / ID）后截断到 `RerankTopK`，`kept_by` 结果追加在后。

### 9.4 过召回（Over-recall）

```
MatchCount <= 0        → DefaultRetrievalTopK = 50
matchCount             = max(MatchCount × 5, 50) × 知识库数，上限 maxRetrievalPoolSize = 500
图片召回 TopK          = TopK × 1.5，上限 500，阈值 min(VectorThreshold, 0.1)
图片不足时             refillPastDroppedImages 翻倍 TopK 回填
```

### 9.5 查询扩展

- `EnableQueryExpansion` 开启后**不调用 LLM**，纯本地生成变体：去停用词、词序重排、关键短语；
- 中文用 jieba `CutForSearch`；
- 关键词路开 hybrid 时阈值 ×0.8、TopK = `max(EmbeddingTopK, RerankTopK) × 2`；
- 16 路并发。

### 9.6 历史引用注入（`merge_history.go`）

- 重叠系数 `|q ∩ c| / min(|q|, |c|) ≥ 0.3` 的历史引用会被注入；
- 分数 ×0.6，最多 3 条，`MatchType = MatchTypeHistory`。

### 9.7 FAQ / Wiki / 图谱对检索的增强

- **FAQ 优先**：`FAQPriorityEnabled` + `FAQDirectAnswerThreshold`（命中即直接作答，不进 LLM 生成）+ `FAQScoreBoost`；
- **Wiki boost**：`PluginWikiBoost` 在重排阶段给 Wiki 命中加权；
- **图谱**：向量/关键词结果之外补充**关系上下文**；
- FAQ 匹配同时走向量 + 关键词 + 标签优先级；**反例问精确命中直接排除**；返回匹配问、分数、命中类型。

### 9.8 对原型的启示

检索测试页是知识库产品的"开发者工具"，必须有：

1. **四段结果**：向量 / 关键词 / 融合（RRF）/ 重排后；
2. **每条显示**：分数、来源文档、块序号、命中高亮、`MatchType`；
3. **可调**：TopK、阈值、向量/关键词权重、是否开 MMR/查询扩展；
4. **可解释**：命中原因（"标题命中 + 语义相似 0.82"）；
5. **可反馈**：单条"答非所问 / 应该召回"，作为后续评估集来源。

## 10. RAG 问答链路

### 10.1 阶段化 Pipeline

```
LOAD_HISTORY
  → MEMORY_RECALL
  → QUERY_UNDERSTAND（改写 / 扩展 / 意图）
  → CHUNK_SEARCH_PARALLEL（多库并行召回）
  → CHUNK_RERANK（PluginRerank → PluginWikiBoost → PluginMemoryAffinity）
  → WEB_FETCH（可选联网补充）
  → CHUNK_MERGE
  → FILTER_TOP_K
  → DATA_ANALYSIS（可选，表格/数值）
  → INTO_CHAT_MESSAGE（组装上下文 + 引用编号）
  → CHAT_COMPLETION / CHAT_COMPLETION_STREAM
```

`PipelineRequest` 主要参数：知识库/文档 ID、`SearchTargets`、阈值、`EmbeddingTopK`、`Rerank*`、`ChatModelID`、`SummaryConfig`、`FallbackStrategy`、`CitationEnabled`、改写/扩展开关、FAQ 策略、`DataAnalysisEnabled`、多模态（`Images` / `VLMModelID` / `ChatModelSupportsVision`）、联网搜索/抓取。

### 10.2 流式与引用

- SSE，`response_type` 区分事件；支持继续生成 / 停止；
- 引用编号可**别名重排**（同一文档多次引用合并）；
- 引用可点击回到原文位置高亮：PDF 文本 → 页码 + 段落框；扫描 PDF 走 MinerU/PaddleOCR-VL；图片 → 原图定位。

### 10.3 对话体验

| 能力 | 说明 |
|------|------|
| 知识库问答 / 附件问答 | 可只针对附件提问，不落库 |
| 引用面板 | 右侧展开，显示原文片段与位置 |
| 中途追加指令 | 生成过程中可追加，不打断 |
| 分叉 / 回滚 | 从任意消息分叉新会话或回滚 |
| 问题大纲 + 历史搜索 | 长会话导航 |
| 复制为 Markdown | 导出 |
| 侧栏助手 | 独立历史、多 Agent 任务切换、审批卡片刷新后保留、后台 shell 任务 |
| 处理阶段 | 附件解析 / 检索 / 工具调用 / 回答，可折叠 |
| 推理与工具输出 | 可折叠展示思考过程、命令输出、文件写入 |
| 追问建议 | 生成 3 条后续问题 |

### 10.4 对原型的启示

问答页不是"聊天框"，而是**三栏**：左（会话/大纲）、中（消息流 + 阶段时间线）、右（引用面板）。这与我们现有「智能诊断」的 Copilot 侧栏形态可以直接复用，但**知识库问答应当是主视图**，不是浮窗。

## 11. FAQ / Wiki / 知识图谱

### 11.1 FAQ

- 结构：**标准问 + 相似问（多条）+ 反例问（多条）+ 答案（多条，全用/随机）+ 单标签分类**；
- 支持启用/停用、**禁止被推荐**；
- 导入：Excel / CSV，`mode = append | replace`，支持 `dry_run`；按内容哈希去重/合并；
- 导入结果：`success / failed / partial_failed / skipped / merged / added` + `failed_entries[]`；
- 导出：CSV（带 BOM）/ JSON；
- `task_id` 限 `[A-Za-z0-9_-]`、≤128 字符。

> 原型：FAQ 模块要"轻"——列表 + 行内编辑 + 批量导入向导（三步：上传 → 校验预览 → 确认导入）。反例问是差异化能力，UI 上要和相似问分开展示并解释作用。

### 11.2 Wiki

- 从文档自动生成 Markdown 页面，形成**左侧树 + 右侧正文**；
- 异步生成，生成中显示"索引中"面包屑；
- 抽取粒度：`focused / standard / exhaustive`（对应 ingest 并发 5/10/10/4，`max_pages_per_ingest` 限制单次页数）；
- 可编辑，带**版本历史与回滚**，来源标记 `auto / agent / manual / rollback`；
- 版本清理：保留 50 条、硬上限 200；
- 独立的 **Wiki 图谱视图**（区别于知识图谱）；
- 删除知识库级联删除页面与版本；
- 工具：`knowledge.create_manual` / `knowledge.create_from_url` / `wiki_write_page` / `wiki_replace_text` / `knowledge.get_parse_progress`；
- 默认生成草稿（不入索引）。

### 11.3 知识图谱

- 入库时抽取实体与关系；
- 依赖 Neo4j + APOC；
- 双层门禁：`NEO4J_ENABLE`（全局）+ KB `graph_enabled`；
- 检索时在向量/关键词之外补充**关系上下文**，用于多跳问题。

> 原型：图谱属于"高阶能力"，建议放在知识库设置的"实验性"区，默认关闭，避免主流程复杂化。

| 维度 | 机制 |

## 14. 对「智能知识库」原型的设计结论

### 14.1 形态：单入口 + 顶部模块切换

保留现有「智能诊断」的 `PlatformShell`（顶栏 + 左侧产品导航 + 内容区），把内容区改为**一个知识库工作台**，顶部用 Tab 切换模块：

```
智能应用 / 智能知识库
┌──────────────────────────────────────────────────────────┐
│ 智能知识库   [知识库名称 ▾]                 搜索  帮助  头像 │
├──────────────────────────────────────────────────────────┤
│ 概览 | 文档 | 分块 | 检索测试 | 问答 | FAQ | Wiki | 设置      │
├──────────────────────────────────────────────────────────┤
│                                                          │
│                     模块内容区                            │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**理由**：WeKnora 的"知识库列表 → 详情 → 子页签"在单库场景下多了一层跳转；我们是单入口应用，把"选库"降级为顶部下拉，主体直接进入工作台。

### 14.2 模块取舍

| 模块 | 是否保留 | 说明 |
|------|---------|------|
| 概览 | ✅ 新增 | 库健康度：文档数/分块数/索引状态/存储/最近活动/待处理失败 |
| 文档 | ✅ | 列表 + 文件夹 + 上传任务面板 + 解析时间线 |
| 分块 | ✅ | 分块列表 + 编辑 + 版本历史 + 分块预览 |
| 检索测试 | ✅ 新增 | 四段结果 + 参数调节 + 反馈 |
| 问答 | ✅ | 三栏：会话/消息/引用 |
| FAQ | ✅ | 独立库类型或库内 Tab（待定） |
| Wiki | ⚠️ 二期 | 高成本，先留入口占位 |
| 知识图谱 | ⚠️ 二期/实验 | 默认关闭 |
| 评估 | ⚠️ 二期 | 先做结果对比表 |
| 设置 | ✅ | 基础信息 / 分块 / 索引 / 模型 / 权限 / 活动 |
| 告警中心 | ❌ 移除 | 与知识库无关（继承自智能诊断） |
| 工具管理 / 技能管理 | ❌ 移除 | 属于 Agent 平台能力，不属于知识库 |
| 模型管理 | ➡️ 降级 | 收敛进"设置 → 模型" |

### 14.3 需要向用户确认的三件事

1. **智能知识库与智能诊断的关系**：知识库是否作为智能诊断 Copilot 的 RAG 数据源？如果是，需要在知识库侧体现"被哪些应用引用"。
2. **FAQ / Wiki 是否本期做**：两者都会显著增加页面量，建议一期只做 FAQ 列表 + 导入，Wiki 留占位。
3. **多知识库还是单知识库**：单入口下是否需要"库列表"？当前设计用顶部下拉承载多库，若确定只有单库可去掉。

## 15. 与「智能诊断」基线的差异清单

| 项 | 智能诊断（基线） | 智能知识库（目标） |
|----|-----------------|-------------------|
| 主导航 | 模型管理 / 工具管理 / 技能管理 / 配置管理 / 告警中心 | 概览 / 文档 / 分块 / 检索测试 / 问答 / FAQ / Wiki / 设置 |
