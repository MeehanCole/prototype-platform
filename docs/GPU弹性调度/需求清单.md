# GPU 指标弹性调度 - 需求清单（v3）

> 状态：**A1 需求清单（v3，待人工确认）** · 模式 A（正向设计，从零）
> 客户需求原文：基于 GPU 指标的弹性调度，**结合目前的 HPA、KEDA 即可**；当前使用 Ray 自带弹性扩缩容
> 架构口径（客户确认）：**Prometheus 指标 → KEDA → 扩缩 Ray，不是扩 Pod**；HPA 是 KEDA 生成的执行器

---

## 1. 业务背景

### 1.1 现状链路

| 层 | 组件 | 职责 | 现状 |
|---|---|---|---|
| 指标 | DCGM Exporter / Ray metrics → Prometheus | 采集 GPU 与 Ray 指标 | 已具备（需确认覆盖面） |
| 决策 | **KEDA**（prometheus scaler） | 按 PromQL + 阈值判定是否扩缩 | 已在用 |
| 执行 | HPA controller（KEDA 生成） | 把期望副本写入目标 | 已在用（作为 KEDA 的手） |
| 目标 | **Ray**（RayCluster worker replicas） | 实际增减 worker | 客户要扩缩的对象 |
| 干扰 | Ray 自带 Autoscaler（in-tree） | 也改 worker 副本 | 已启用 → 潜在双写 |

### 1.2 痛点

1. **GPU 指标未接入决策链**：扩缩看的是其他信号，GPU 打满/显存快爆不触发
2. **信号选错就会反向扩**：`GPU_UTIL` 是「kernel 活跃时间占比」，batch 打满 100% 属正常，按它扩容会无限扩
3. **双大脑**：KEDA 与 Ray in-tree autoscaler 都改同一批 worker → 副本震荡、任务被杀
4. **决策不可解释**：运维不知道断在「指标→KEDA→HPA→Ray」哪一环
5. **执行接口缺口**：KEDA 扩 CRD 需要 `/scale` 子资源，RayCluster 是否具备待核实；RayService 已确认不可行

### 1.3 目标

把 GPU 指标接进 KEDA 的决策链，让扩缩准确落到 Ray 上；做到信号可配、决策可解释、双写不打架。**不新造扩缩容引擎。**

## 3. 功能点清单（MoSCoW）

### Must Have

- [ ] **FR-1 GPU 指标面板**：DCGM 口径（GPU_UTIL / 显存 used,total / SM_ACTIVE / Tensor Core / 功耗）+ Ray 应用指标；支持 功能区/云实例/应用/单卡 下钻；标注「利用率 ≠ 算力饱和度」
- [ ] **FR-2 KEDA 弹性策略配置**：PromQL、`threshold`、`activationThreshold`、`pollingInterval`、`cooldownPeriod`、min/max worker；展示 KEDA→HPA→Ray 执行链与接入方式（A 直扩 RayCluster / B external scaler / C 仅调上限）
- [ ] **FR-3 弹性决策留痕**：时间线「指标值 → 是否 Active → HPA 期望副本 → Ray 实际 worker → 结果/失败原因」
- [ ] **FR-4 扩缩信号口径**：主信号用压力类（队列深度 / ongoing requests / KV cache 占比），GPU 指标辅助；可配阈值、步长、冷静期
- [ ] **FR-5 双写防护**：识别 Ray in-tree autoscaler 与 KEDA 同时管理同一 RayCluster，冲突阻断 + 处置建议

### Should Have

- [ ] **FR-6 策略预设**：保守/均衡/激进，展开可见参数，一键套用
- [ ] **FR-7 指标链路健康与冻结**：Exporter/Prometheus 不可达 → 冻结弹性 + 告警；禁止把「无数据」当低负载缩容
- [ ] **FR-8 上限与配额校验**：max worker × 每 worker 卡数 ≤ 租户配额 / 功能区容量
- [ ] **FR-9 缩 worker 优雅退出**：承载 actor/Serve 副本的 worker 不可直缩；提示 SIGTERM / checkpoint / idle 判定

### Could Have

- [ ] **FR-10 参数建议**：基于历史曲线推荐阈值与 max worker，仅建议
- [ ] **FR-11 回放 / A-B 对比**：worker 曲线、GPU 利用率、扩容等待时间对比

### Won't Have

- [ ] 扩 K8s Pod 作为主路径（客户明确排除）
- [ ] 直接扩 RayService（`num_replicas` 在 `serveConfigV2` 字符串内，无 `/scale`）
- [ ] 自研扩缩容算法 / reimplement KEDA
- [ ] 纯 CPU 弹性；作业卡数弹性；跨功能区迁移

## 4. 技术约束（详见技术调研）

| 项 | 约束 |
|---|---|
| 指标来源 | NVIDIA DCGM Exporter → Prometheus；Ray 侧另有 `ray_serve_*` 指标 |
| KEDA 语义 | `IsActive` 管 0↔1（activationThreshold 须「大于」）；1↔N 由生成的 HPA 执行；`minReplicaCount>=1` 时激活阈值失效 |
| 执行接口 | RayCluster `/scale` 子资源**待核实**；RayService **不可行** |
| 双写 | Ray `enableInTreeAutoscaling` 与 KEDA 会同时改 worker 副本 |
| 缩容 | HPA 随机挑副本终止，长任务需优雅退出 |
| 前端 | 平台基座 Vite + React + Tailwind/Shadcn token；设计系统预设待 A4 |
