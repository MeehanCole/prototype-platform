# AI 设计工作流指南

## 概述

原型平台支持三种设计工作流，覆盖从 0 到 1 的新产品设计与从 1 到 N 的已有产品迭代。每种模式有明确的起点、AI 介入点、人工决策点和产物规范。

## 模式选择决策树

```
你的起点是什么？
├─ 只有业务需求/想法 → 模式 A 正向设计
├─ 有截图/设计稿/Figma → 模式 B 逆向设计
└─ 已有产品 + 新需求 → 模式 C 混合模式
```

| 场景 | 推荐模式 | 理由 |
|------|---------|------|
| 新产品 MVP 验证 | A | 需要从需求推导方案 |
| 竞品功能复刻 | B | 有参照物，直接还原 |
| 已有产品新增模块 | C | 需要还原现有 + 改造新增 |
| 设计稿评审 | B | 设计稿转可交互原型 |
| 需求评审 | A | 从需求生成方案对比 |
| 版本迭代 | C | 基于现有版本改造 |

---

## 模式 A：正向设计

**起点**：业务需求/用户故事/想法
**终点**：原型 + PRD 文档
**AI 价值**：需求拆解、竞品分析、方案生成、原型代码生成

### 流程

#### A1 需求输入
**输入物**：业务需求描述（口头/文字/用户故事）
**AI 任务**：结构化需求，补充隐性需求
**产物**：`requirement.md` 需求清单

关键问题：
- 用户是谁？角色有哪些？
- 核心目标是什么？解决什么问题？
- 有哪些约束（预算/时间/技术）？

#### A2 需求分析
**输入物**：需求清单
**AI 任务**：竞品分析、深度调研、需求优先级排序
**产物**：`analysis.md` 分析报告

分析维度：
- 竞品分析：列出 3-5 个同类产品，对比核心功能差异
- 用户路径：用户完成目标的操作步骤
- 需求优先级：MoSCoW 法（Must/Should/Could/Won't）
- 技术可行性：识别技术难点和依赖

#### A3 方案设计
**输入物**：分析报告
**AI 任务**：生成 2-3 个候选方案，对比优劣
**产物**：`solutions.md` 方案对比文档 + 决策记录

⚠️ **人工决策点**：AI 生成多方案后，必须由人选择最终方案。AI 不应替人做业务决策。

方案对比维度：
- 用户体验：操作步骤数、学习成本
- 开发成本：技术复杂度、工时估算
- 风险：技术风险、业务风险
- 扩展性：未来迭代空间

#### A4 原型生成
**输入物**：选定的方案
**AI 任务**：调用 `prototype-page-generator` Skill 生成原型代码
**产物**：`src/pages/<Module>/<Page>/` 原型页面

生成要求：
- 遵循 Skill 规范（目录约定、默认导出、meta.json）
- 选择匹配的设计系统预设
- 生成空状态、加载状态、错误状态
- 生成 PRD 初稿（包含业务上下文）

⚠️ **人工校验点**：AI 补充的交互细节可能不符预期，需人工微调。

#### A5 PRD 文档
**输入物**：原型 + 方案文档
**AI 任务**：整合分析报告、方案决策、原型交互，输出结构化 PRD
**产物**：`prd.md` 完整 PRD 文档

PRD 必须包含：
- Business Context（业务上下文）
- Feature Overview（功能概述）
- Functional Requirements（功能需求）
- Interaction Flow（交互流程）
- Edge Cases（边界情况）
- Component Mapping（组件映射，可选）

## 模式 B：逆向设计

**起点**：截图/设计稿/Figma 文件
**终点**：原型 + PRD 文档
**AI 价值**：视觉还原、代码生成、规范适配

### 流程

#### B1 输入采集
**输入物**：Figma 链接 / 截图图片 / 设计稿文件
**AI 任务**：识别页面结构、组件、布局
**产物**：页面结构描述

输入类型：
- Figma 链接：调用 `figma-implement-design` 读取设计稿
- 截图图片：AI 视觉识别 + 代码生成
- 已有代码（Locofy 等导出）：调用适配器改造

##### B1.1 关键决策：截图来源 → 还原路径选择
用户给截图还原时，**必须先选择还原路径**，避免直接硬编码颜色导致后续改造困难：

| 路径 | 适用条件 | 还原方式 | 速度 | 后续可迭代性 | 推荐度 |
|---|---|---|---|---|---|
| ① 截图 → **直接出代码**（90% 场景推荐） | 改动面小（< 30% 结构变动）、一次性交付、不需要设计师反复微调 | AI 视觉识别布局 → **先识别截图属于哪套设计系统 preset**（Element Plus / Ant Design / Arco / Naive / 默认）→ 用对应 preset 的 token 出代码 → B3 规范适配 | 快 | 中 | ✅ 推荐默认 |
| ② 截图 → Figma 设计稿 → 代码（10% 大改场景） | 改动面大 > 30%、后续至少迭代 2 版、需要和设计师协作 | AI 视觉把截图转成 Figma 结构化组件 → 设计师人工微调对齐规范 → `figma-implement-design` 出代码 | 慢 | 高 | 大改场景推荐 |

决策引导提问（AI/BOT 在 B1 阶段**必须问用户**再往下走）：
1. 「这次还原后改造的变动面有多大？小改（加几个模块/字段）还是大改（信息架构整体调整）？」
2. 「截图看起来对齐的是哪套设计系统？Element Plus / Ant Design / Arco Design / Naive UI / 都不是？」→ 对应用 `src/host/design-systems/presets.ts` 里的预设

#### B1.2 Mode C 基线来源的三种形式（= 输入物是什么都行）
Mode C 混合模式的起点是「已有产品 + 新需求」，**「已有产品」不一定必须是代码，三种形式都能作为 C1 基线**：
| 已有产品形式 | C1 处理方式 | 说明 |
|---|---|---|
| 已有原型代码 | 直接放入目录 → `_versions/v1.tsx` 快照 → 进入 C2 | 本项目内历史生成页面用此方式 |
| 截图几张 | 先执行 Mode B B1.1 决策 → 走 B 路径还原成代码 → 作为 v1 基线 → 进入 C2 | 外部产品截图 / 甩图改造场景 |
| Figma 链接 | `figma-implement-design` + B3 适配 → 作为 v1 基线 → 进入 C2 | 设计师有现成设计稿场景 |

⚠️ **C1 基线校验产物**：不管哪条路径，C1 结束时必须产出以下三项才能进 C2：
1. `index.tsx`（基线代码）
2. `_versions/v1.tsx`（基线快照留档）
3. `prd_v1.md`（基线简版 PRD，后续 C5 对比用）

#### B1.3 批量截图还原（≥ 5 张截图时的标准流程，禁止直接全量生成代码）
真实业务场景往往不是一张截图，而是「一个功能一套截图 + 弹窗/空状态/筛选态 N 张」共 N 张。**严禁直接扔一堆截图给 AI 让它全量生成代码**——结果必然目录混乱、页面命名乱、组件重复、次要页面浪费太多精度人力。必须按以下 5 步流程走：

---

##### Step 1：截图聚类成页面（预处理第 1 步，先整理，不写代码，1-2 小时）
把所有截图扔到一个文件夹，人工 + AI 视觉做一次聚类，产出 **「截图-页面映射表」**（Markdown/Excel 均可）。**同一页面不同状态（展开筛选、弹窗、分页、空态）算 1 页，不算多页。**

映射表模板：
| 序号 | 页面名称 | 模块归属 | 对应截图文件 | 优先级 | 还原精度 | 关联页面 | 备注（弹窗/特殊态） |
|---|---|---|---|---|---|---|---|
| 1 | 审批中心首页 | OA | 01_home.jpg, 02_filter_open.jpg, 03_todo_modal.jpg | P0（核心） | 🔴 高精度 | 审批详情 | 有 1 个催办弹窗 |
| 2 | 审批详情 | OA | 04_detail.jpg, 05_timeline_expand.jpg | P0 | 🔴 高精度 | 审批中心 | 有时间线展开 |
| 3 | 提交请假单 | OA | 11_leave_form.jpg, 12_datepicker.jpg | P0 | 🔴 高精度 | 我的申请 | 日期选择器 |
| 4 | 提交报销单 | OA | 13_expense.jpg, 14_upload_receipt.jpg | P1 | 🟡 中精度 | 我的申请 | 票据上传 |
| 5 | 我的申请列表 | OA | 21_mine_list.jpg | P1 | 🟡 中精度 | 详情页 | |
| 6 | 抄送我列表 | OA | 31_cc_list.jpg | P2 | 🟢 低保真 | | 纯列表 |
| 7 | 个人设置-账号 | 账号 | 41_settings.jpg | P2 | 🟢 低保真 | | |

##### Step 2：还原精度分级（预处理第 2 步，省一半时间的核心）
**不要所有页面都做逐像素还原——90% 场景下 20% 核心页面值得做高精度，其余 80% 用中/低保真即可。**
| 精度 | 适用 | 还原要求 | 耗时比（相对高精度） |
|---|---|---|---|
| 🔴 高精度（逐像素） | P0 核心页 / Mode C 要改造的页 / 需要演示的页 | 布局、组件、弹窗、空态、分页、交互细节全还原；严格对齐 design system preset；mock 数据填真实业务样例 | 1x（基准） |
| 🟡 中精度（结构对视觉对齐） | P1 次要业务页，后续不改造，只作为上下文导航 | 主要布局 + 组件类型正确，视觉大致对齐；数据简单占位；空态/分页可以不做 | 0.4x |
| 🟢 低保真（骨架草图） | P2 设置页/帮助页/流程末端列表 | 只画布局骨架，组件类型对就行，不卡视觉；文字用 lorem，甚至部分模块不画 | 0.15x |

> 💡 经验法则：30 张截图聚类后 ≈ 10 个页面。按 P0×3 + P1×5 + P2×2 配比 → 3×1 + 5×0.4 + 2×0.15 = 5.3 人日。如果 10 个页面全 🔴 高精度 → 10 人日，**分级直接省一半人力**。

##### Step 3：批次还原（Skill 逐页调用，不要合并 prompt）
顺序：**先 P0 → 再 P1 → 最后 P2**。每个页面单独走一次标准 B 流程（B1.1 决策 → B2 还原 → B3 适配 → B4 接入），严禁把 10 个页面塞在同一个大 prompt 里让 AI 一次性输出（会漏掉分页、弹窗、命名冲突）。

每个批次输出物：
- 每个页面对应一个 `src/pages/<Module>/<PageName>/` 目录
- 每个页面独立的 `meta.json` / `index.tsx` / `prd.md`

##### Step 4：跨页面一致性修正（批量还原后必做 1 步，否则会乱）
所有页面还原完后，统一过一次 **跨页面一致性 Checklist**：
- [ ] 侧边栏 / Header / Footer 全局组件三套是否同一套（不要每个页面自己写）
- [ ] 所有页面的主按钮样式 / 圆角 / 高度一致（高精度 vs 中精度页经常有差异）
- [ ] 弹窗遮罩、Toast、空态插画等全局公共样式一致
- [ ] 面包屑、导航层级、路由跳转逻辑正确
- [ ] 所有 P0 页面的 design system preset token 用的是同一套（不要页面 A 用 Element Plus 蓝、页面 B 用 AntD 蓝）

##### Step 5：Mode C 专属优化 — 哪些页面做 V1 快照？
如果是 Mode C 批量还原后要加新需求，**不是所有页都做 `_versions/v1.tsx` 快照**，只做：
1. 新需求直接触碰到的 P0 页面（改代码的页）
2. 全局入口页 / 导航页（有导航跳转关系的）
其余 P1/P2 页不做版本留档，省空间省时间。

#### B2 视觉还原
**输入物**：页面结构描述
**AI 任务**：生成 React + Tailwind 代码
**产物**：原始原型代码

还原要求：
- 布局结构：flex/grid 布局，禁止绝对定位
- 组件识别：识别按钮/表单/表格等通用组件
- 间距系统：8pt grid 对齐
- 响应式：基础响应式适配

#### B3 规范适配
**输入物**：原始原型代码
**AI 任务**：调用 `prototype-page-generator` Skill 的适配规则改造
**产物**：符合平台规范的代码

适配清单（自动校验）：
- [ ] 默认导出 `export default function`
- [ ] 创建 `meta.json`（title + module）
- [ ] 移除外部 UI 库依赖（MUI/AntD/Emotion）
- [ ] 颜色映射到设计 token
- [ ] 注释使用 ASCII 标点
- [ ] `node scripts/validate-page.js` 通过

#### B4 平台接入
**输入物**：规范代码
**AI 任务**：放入 `src/pages/` 目录，自动注册路由
**产物**：平台可访问的原型页面

#### B5 反向 PRD
**输入物**：还原的原型
**AI 任务**：从原型反推 PRD，追问设计意图
**产物**：`prd.md` PRD 文档

⚠️ **关键追问**：PRD 不能只是"描述原型上有什么"，必须追问：

- **为什么**这样设计？（业务理由）
- **数据从哪来**？（接口/状态/计算逻辑）
- **边界情况**？（空/超长/并发/失败）
- **异常处理**？（网络错误/权限不足/数据冲突）
- **后续扩展**？（未来可能增加什么）

反向 PRD 模板：
```markdown
# <页面标题> PRD

## Business Context
**Target product**: <产品名>
**Target tech stack**: <技术栈>
**Design system**: <设计系统>
**Entry point**: <在产品中的位置>
**Related existing pages**: <关联页面>

## Feature Overview
<这个页面做什么，2-3 句话>

## Functional Requirements
| 区域 | 功能 | 数据来源 | 说明 |
|------|------|---------|------|
| ... | ... | ... | ... |

## Interaction Flow
1. <操作步骤>

## Edge Cases
- 空状态：<如何展示>
- 加载状态：<如何展示>
- 错误状态：<如何展示>
- 边界值：<如何处理>

## Design Intent
<为什么这样设计，业务理由>

## Future Extension
<未来可能扩展的方向>
```

## 模式 C：混合模式

**起点**：已有产品（截图/代码）+ 新需求
**终点**：改造后的原型 + 完整 PRD
**AI 价值**：上下文还原 + 需求叠加 + 改造生成

### 流程

#### C1 现有产品还原（= B1-B4）
按模式 B 还原现有界面，建立"上下文基线"。
**产物**：现有界面原型（作为改造基准）

#### C2 新需求分析（= A1-A2）
按模式 A 分析新需求，明确改造目标。
**产物**：`requirement.md` + `analysis.md`

#### C3 改造方案设计
**输入物**：现有原型 + 新需求分析
**AI 任务**：设计改造方案，标注"改哪里、为什么改、改完什么样"
**产物**：`solutions.md` 改造方案

改造类型：
- **新增**：在现有界面增加新模块/功能
- **修改**：调整现有功能的交互/视觉
- **删除**：移除不再需要的功能
- **重组**：调整信息架构/导航结构

⚠️ **人工决策点**：改造方案需确认，尤其是"删除"和"重组"类型。

#### C4 原型改造
**输入物**：改造方案 + 现有原型
**AI 任务**：在现有原型基础上修改，保留未改动部分
**产物**：改造后的原型

改造原则：
- 最小改动：只改需要改的，不动其他
- 版本对比：保留改造前版本，支持 A/B 对比
- 向后兼容：不破坏现有交互流程

#### C5 完整 PRD + 功能点内嵌

**输入物**：改造后的原型 + 改造方案
**AI 任务**：输出包含"现有功能 + 新增功能"的完整 PRD，并将 PRD 业务描述内嵌到原型代码
**产物**：`prd.md`（或 `prd_v2.md`）+ 功能点标注代码

PRD 结构：
- 现有功能描述（简要）
- 新增/修改功能（详细）
- 改动影响分析（对现有功能的影响）
- 迁移/兼容说明（如有）

**PRD 内嵌代码规范**（Mode C 强制）：
1. PRD 中每个功能需求加 `**FR-X` 标记段落起始
2. 版本文件 `import prdRaw from '../prd_v2.md?raw'`
3. 包含 `extractSection` 工具函数按 FR 段落提取
4. `FEATURE_DOCS` 映射表（key 与 `FEATURE_LABELS` 1:1）
5. 功能点标注为胶囊形「说明」按钮：蓝色可点击 → 弹出 DocPanel 展示完整 PRD
6. DocPanel 用 `createPortal` 渲染到 `document.body`，支持 Esc + 遮罩关闭

**测试验收 Changelog**（Mode C 强制）：
- 生成 `c5_v1_vs_v2_changelog.md`，6 节结构
- 编号对齐：Changelog 编号 = FEATURE_LABELS key = 原型按钮编号
- 测试流程：开「显示新增功能点」→ 逐个点击「说明」按钮 → 对照 Changelog 验收

## 产物目录结构

每个项目的工作流产物集中存放：

```
src/pages/<Module>/<Page>/
  ├── index.tsx              # 原型代码
  ├── meta.json              # 页面元数据
  ├── prd.md                 # 最终 PRD（单版本）
  ├── prd_v1.md              # 多版本 PRD（含 **FR-X 标记）
  ├── prd_v2.md
  ├── _versions/             # 多版本原型
```

## 与 Skill / 项目规则的关系

本工作流的完整规范和代码模板以 **项目级 `.skills/` 目录**为准:

| 文件 | 内容 |
|---|---|
| `.skills/design-workflow.md` | 本工作流的完整规则(模式 A/B/C 详细步骤、版本管理、产物目录) |
| `.skills/page-generator.md` | 代码生成契约(目录约定、默认导出、样式系统、PRD 内嵌、DocPanel) |
| `.skills/templates.md` | 可复制的代码模板(meta.json、PRD、Changelog、extractSection、DocPanel、NewTag) |

Skill 职责:
1. **识别用户起点**：判断属于模式 A/B/C
2. **引导执行流程**：按对应模式的步骤推进
3. **调用其他 Skill**：在需要时调用 `prototype-page-generator`、`figma-implement-design`
4. **生成过程产物**：填充各阶段模板
5. **校验产物完整性**：检查每阶段产物是否齐全

**跨 IDE 兼容**：`.trae/skills/` 是 Trae IDE 的 Skill 适配器,`.skills/` 是项目级通用规则。换 IDE 时直接引用 `.skills/` 下的文件即可。
