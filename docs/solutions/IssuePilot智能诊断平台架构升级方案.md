# IssuePilot 智能诊断平台 — 架构升级方案

## 一、现状分析

### 1.1 旧架构（Electron 桌面端）

```
┌─────────────────────────────────────────────────────┐
│              Electron 桌面客户端                      │
│  ┌───────────┐  ┌───────────┐  ┌─────────────────┐  │
│  │ 对话模式   │  │ 诊断模式   │  │ 智能对话交互     │  │
│  └───────────┘  └───────────┘  └─────────────────┘  │
└──────────────────────┬──────────────────────────────┘
                       │ HTTP
┌──────────────────────▼──────────────────────────────┐
│            Python Server (本地进程)                    │
│  ┌─────────────┐ ┌─────────────┐ ┌──────────────┐  │
│  │ 模型管理     │ │ 工具管理     │ │ 工作流管理    │  │
│  └─────────────┘ └─────────────┘ └──────────────┘  │
│  ┌─────────────┐ ┌─────────────┐ ┌──────────────┐  │
│  │ 智能体管理   │ │ 插件管理     │ │ issuePilot   │  │
│  └─────────────┘ └─────────────┘ └──────────────┘  │
└──────────────────────┬──────────────────────────────┘
                       │
              ┌────────▼────────┐
              │   PostgreSQL     │
              └─────────────────┘
```

**旧架构痛点**：
| # | 痛点 | 影响 |
|---|------|------|
| 1 | 桌面端部署，每个用户需单独安装 | 运维成本高，无法快速推广 |
| 2 | 本地 Python Server，模型/工具绑定单机 | 无法共享算力，资源利用率低 |
| 3 | 无多租户隔离 | 不支持团队协作和权限分级 |
| 4 | 算力调度靠手工 | GPU 资源争抢，无队列管理 |
| 5 | 无平台级集成 | 与 KubeSphere/Hami/Ray 割裂 |
| 6 | 无技能（Skill）管理 | 复用逻辑只能靠复制工作流 |
| 7 | 运维能力弱 | 日志/监控/告警需手动排查 |

## 二、差距分析（Gap Analysis）

### 2.1 功能模块对比

| 模块 | 旧架构 | 新架构目标 | 差距 | 迁移方式 |
|------|--------|-----------|------|---------|
| **模型管理** | 本地配置 | 平台级模型目录 + GPU 调度 | 需对接 Hami+Ray | 新增 ModelService 对接算力平台 |
| **工具管理** | 本地 MCP Server | 平台级 MCP 服务注册中心 | 需服务发现 | MCP 工具 → K8s Service + 注册中心 |
| **工作流管理** | 本地 LangGraph | 容器化 LangGraph 引擎 | 需状态持久化 | LangGraph Server 化 + Redis 状态 |
| **智能体管理** | 本地配置 | 多租户智能体 + 权限 | 需多租户隔离 | 智能体 CRUD + OIDC 权限绑定 |
| **技能管理** | ❌ 无 | ✅ Skill 库（新增） | 全新开发 | Skill 模板 + 版本管理 |
| **插件管理** | 本地 SSH/Headlamp | 平台级插件服务 | 需服务化 | 插件 → Sidecar 模式 |
| **对话交互** | Electron 窗口 | Web Chat UI | 前端重写 | React Chat 组件 + SSE 流式 |
| **数据存储** | 本地 PostgreSQL | 平台 PostgreSQL + 对象存储 | 数据迁移 | 数据导出 → 平台 DB 导入 |
| **认证** | 无/简单密码 | OIDC（Keycloak） | 全新对接 | 前端 OIDC 登录 + 后端 Token 校验 |
| **运维** | ❌ 无 | 日志/监控/告警/巡检 | 全新开发 | 对接 K8s 日志/监控 API |
| **资源管理** | ❌ 无 | 创建云资源（对接 K8s） | 全新开发 | K8s API 封装 + 资源模板 |

### 2.2 技术架构对比

| 维度 | 旧架构 | 新架构 | 改造量 |
|------|--------|--------|--------|
| **部署形态** | 桌面安装包 | K8s Deployment + Ingress | 🔴 全改 |
| **前端** | Electron（React） | React Web App | 🟡 复用 70% 组件 |
| **后端** | Python 单体 | Python 微服务（FastAPI + 插件） | 🟡 拆分为服务 |
| **通信** | HTTP localhost | REST + SSE + WebSocket | 🟡 改接口 |
| **状态存储** | SQLite/PostgreSQL 本地 | 平台 PostgreSQL + Redis | 🟡 迁移 |
| **算力调度** | 手动 | Hami + Ray + Queue | 🔴 新增 |
| **认证鉴权** | 无 | OIDC + RBAC | 🔴 新增 |
| **MCP** | 本地进程 | K8s Service 化 | 🟡 适配 |
| **LangGraph** | 本地运行 | LangGraph Cloud/Server | 🟡 适配 |

## 三、迁移实施路线

### Phase 1：Web 前端 + API 网关（4 周）

```
Week 1-2: Web 前端框架搭建
├── 基于现有 Prototype Platform 搭建 IssuePilot 管理模块
├── 管理面：模型/工具/技能/智能体管理界面
├── 应用面：Agent 对话 + 智能问答界面
└── 运维面：日志/监控/告警/巡检界面

Week 3-4: API 网关 + 认证
├── issuePilot Server 容器化改造
├── Agent API 网关（统一入口）
├── OIDC 对接（Keycloak / Dex）
└── SSE 流式对话接口
```

### Phase 2：服务化改造（4 周）

```

├── ToolService（MCP 注册中心）
├── AgentService（智能体 CRUD + 权限）

├── LangGraph Server 化（Redis 状态持久化）
├── MCP 工具运行时（K8s Service）
├── RAG 知识库（对接 Ragflow）
```

```
Week 9-10: 运维能力

Week 11-12: 灰度上线
├── 数据迁移（PostgreSQL 导出 → 平台导入）
├── MCP 工具迁移（本地 → K8s Service）
├── 灰度发布（10% → 50% → 100%）
└── 回滚预案 + 压力测试
```

## 四、关键技术决策

### 4.1 前端架构

```
技术栈：React + Vite + Tailwind + Shadcn UI
布局：
  - 管理面：侧边栏 + 内容区（与现有平台一致）
  - 应用面：对话式界面（Chat UI）
  - 运维面：仪表盘式布局
路由：基于现有平台路由注册机制
```

### 4.2 后端架构

```
issuePilot Server 拆分为：
├── agent-api          # 统一 API 网关（SSE + REST）
├── model-service       # 模型管理（对接 Hami+Ray）
├── tool-service        # MCP 工具注册中心
├── agent-service       # 智能体 CRUD + 权限
├── skill-service       # 技能模板管理
├── workflow-service    # LangGraph 工作流引擎
├── ragged-service      # RAG 知识库（对接 Ragflow）
└── ops-service         # 运维（日志/监控/告警）

通信：各服务间 gRPC，对外 REST + SSE
存储：PostgreSQL + Redis + MinIO（对象存储）
```

### 4.3 算力调度集成

```
用户请求 → issuePilot Server → Hami Scheduler → Ray Cluster
                                          ↓
                                    GPU 资源调度
                                          ↓
                                    推理/训练任务
                                          ↓
                                    结果回传
```

**关键对接点**：
1. Hami 自定义 Resource：`nvidia.com/gpu` 调度
2. Ray Job Submission API：提交推理任务
3. Queue 优先级：VIP > Normal > Low
4. 算力状态查询：实时 GPU 利用率

### 4.4 MCP 工具服务化

```
旧：MCP Server 进程（本地）
新：MCP Server → K8s Deployment → Service → 注册中心

对接方式：
1. 每个 MCP 工具打包为 K8s Deployment
2. 通过 Service 暴露 HTTP/SSE 端口
3. issuePilot Server 通过服务发现调用
4. 支持热插拔（新增/删除工具无需重启）
```

## 五、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 模型迁移到 Hami+Ray 后延迟增加 | 用户体验下降 | 缓存热点模型 + 预加载 + 批量推理 |
| MCP 工具服务化后调用链路变长 | 诊断速度下降 | 服务网格（Istio）优化 + 本地缓存 |
| 多租户数据隔离不彻底 | 安全事故 | Row-Level Security + 租户 ID 强制过滤 |
| LangGraph 状态持久化不一致 | 工作流中断 | Redis 事务 + 状态快照 + 断点续跑 |
| 灰度期间双写数据不一致 | 数据丢失 | 主写旧库 → 异步同步 → 切主写新库 |
