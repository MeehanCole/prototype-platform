## Feature Overview（描述 + 追问）

> 反向 PRD 的第一步不是复述"有这个功能"，而是先问：**这个页面存在的根本目的是什么？**

### 原型上有什么
一个页面内包含：统计看板（4 卡片）、Tab 分类（4 个）、看板+列表双视图、审批详情弹窗、筛选、批量操作。

### 追问：为什么这个页面要存在？
- **为什么不把审批待办直接放在各业务系统里？** → 多业务系统（报销/请假/采购/用印）的审批流分散在各自页面，用户需要逐个系统打开找待办，跨系统切换成本高。
- **为什么不直接用消息通知（Toast/小红点）代替？** → 消息只能提醒有新待办，不能承载"审批决策+进度查询+历史追溯"的完整工作流。
- **为什么叫"审批中心"而不是"待办列表"？** → "中心"定位比"列表"更重，暗示这是管理性、全局性入口，而不是单纯的任务队列。因此需要统计看板（管理者视角）+ 处理工具（执行者视角）双能力。

## Functional Requirements（逐模块"为什么"）

### 1. 顶部：标题 + 副标题 + 筛选

| 原型上有什么 | 为什么这样设计？ |
|---|---|
| 标题"审批中心" + 副标题"统一处理各业务线审批事项" | 副标题是**价值主张锚点**。新用户进来一眼就懂这个页面和"报销/请假"各自的审批有什么区别——它是跨业务线的**统一入口**。如果只有标题，用户可能怀疑它只是某条业务线的。 |
| 右上角两个下拉：审批类型 / 状态 | 为什么放在标题旁边而不是某个 Tab 下？因为**筛选是全局作用于看板+列表**的，放在最顶部暗示其全局属性，也避免了切换 Tab 时筛选状态丢失的心智复杂度。 |
| 筛选只有 2 项，不是时间范围 / 申请人 / 单号 / 关键词 | 为什么做了"减法"？MVP 阶段用户最高频的筛选维度就是**类型**（我只处理报销）和**状态**（我只看超时）。其他维度（单号精准查、申请人查、时间跨度）大概率是低频冷路径，先不做避免信息过载。 |

### 2. 4 个统计卡片（顶部看板）

| 原型上有什么 | 为什么这样设计？ |
|---|---|
| 4 卡：待办事项 / 超时未处理 / 今日已处理 / 本周已完成 | 4 个数刚好对应管理者关心的 4 个维度：**压力（待办）、风险（超时）、当日产出（今日）、周期进度（本周）**。少了缺维度，多了注意力稀释。 |
| 每卡数字 + 下方趋势小图（Sparkline） + 一行小字（"较昨日 +2"） | 纯数字只告诉你"现在是多少"，趋势告诉你"**方向是什么**"。待办从 3 涨到 5 很紧张、从 7 降到 5 是改善中、今日已处理比昨天多是士气。趋势比单点数字更有决策价值。 |
| 超时卡用橙色趋势线、今日已处理用绿色、待办用主色 | 颜色做了**情绪编码**：超时=警告（橙）、今日已处理=正向（绿）、待办=中性工作色（主色）。用户一眼分辨，不必读文字。 |
| 卡上没有"点击跳转"的视觉暗示（无手型/无箭头） | 为什么统计卡片不能点？因为它和下面 Tab 的数据不是 1:1 映射（本周已完成跨多个 Tab），点击后跳哪里是歧义点，索性不做避免误跳转。等后续明确了"跳对应筛选视图"的语义再增强。 |

### 3. Tab 分类：待办 / 已办 / 抄送我 / 我发起的（带 Badge 数量）

| 原型上有什么 | 为什么这样设计？ |
|---|---|
| 4 Tab 是主流产品标配（钉钉/飞书/企微全这么分） | 为什么不自定义分类？因为用户心智已被竞品训练好——**4 Tab 是行业事实标准**，用户不用学习。改了反而增加认知成本。 |
| Tab 下有主色下划线 + Badge 数量标在 Tab 名后 | 下划线是 **Tab 激活态的视觉锚**，避免在密集 UI 中找不到当前在哪。Badge 的位置（紧贴 Tab 文字后面）比放在右侧更能让用户"读 Tab 名时瞟到数字"——看到"待办 5"的感知是"我有 5 件事要做"，Badge 放在角上会被忽略。 |
| 待办 Tab 的 Badge 用主色，其他 Tab 用灰 | 主色吸引注意力，强化"待办是行动召唤"。已办/抄送/我发起属于"浏览类"，灰 Badge 降低存在感减少噪音。 |

### 4. 看板 + 列表双视图切换

| 原型上有什么 | 为什么这样设计？ |
|---|---|
| 两个视图按钮在同一胶囊容器，激活用白底 + 软阴影 | 样式参考了 iOS SegmentedControl，**视觉上暗示"同一空间的两种呈现方式"**而不是两个独立按钮。用户一看就知道是互斥切换。 |
| 默认看板视图而非列表视图 | 这是**定位选择**——默认管理者视角而非执行者视角。审批中心的"中心"二字决定了它首先是"看全局分布"的入口，然后才是"逐条处理"的工作台。如果默认列表，管理者进来第一眼看不到按类型分布的整体感。 |
| 看板按**类型**分列（请假/报销/采购/用印），不是按**状态**或按**优先级** | 为什么分组维度是类型？因为审批类型和"需要的知识/决策复杂度"强相关——处理报销的人懂财务、处理请假的是部门经理，按类型分组后，审批人可以**批量进入自己熟悉的类型**先处理。按状态分列没意义（待办本来就只剩待处理），按优先级分则优先级定义本身是主观输入不可靠。 |
| 看板列头有色标 Tag + 数字 | 列和 Tab 类似——数字是"这列有多少条"的小锚点，色标让用户在看板+列表来回切换时**快速识别"哪堆是哪类"**，不用每次重读文字。 |
| 列表视图有**勾选列**+分页，看板视图没有 | 因为**批量操作只在列表里发生**。看板是概览工具，列表是处理工具。给看板加勾选会把看板变成"又像概览又像任务队列"的混合体，两边都做不好。 |

### 5. 列表视图：表格

| 原型上有什么 | 为什么这样设计？ |
|---|---|
| 列顺序：勾选 → 标题→ 类型 → 发起人 → 提交时间 → 当前节点 → 状态 → 操作 | 顺序按"**信息读取优先级**"排。用户点进列表第一件事是扫标题判断内容，类型+发起人+时间是辅助识别，当前节点+状态是决策依据，操作放最右是因为不是每行都要点操作。 |
| 表格 stripe（偶数行浅底色）+ headerBg #fafafa | 纯 Element Plus 预设。为什么 stripe 重要？密集数据下**视线定位成本下降**，尤其同一行跨多列读时不容易串行。 |
| 状态 Tag 有四色语义（待审批橙/审批中蓝/已通过绿/已驳回红） | 审批场景下"状态"是最需要被秒读的字段，颜色编码比文字快 10 倍。四色语义也是行业通用，没有自己发明——降低用户学习成本。 |
| 操作列只有待审批行显示"同意/驳回"，其他行只有"详情" | 行内快捷操作有**误触风险**（尤其同意/驳回这种不可逆操作）。对已审批完的行，放快捷操作按钮是噪音，只会让 UI 更乱。 |
| 同意按钮是主色淡色底（10% alpha），驳回是红色淡色底 | 为什么不用实心主色按钮？因为**行内操作是次级按钮**——主路径是"点详情看完再决策"，行内直接同意是"信任快捷通道"。视觉层级做低，暗示"想快可以用，但请先看详情"。 |
| 分页在表格外底部，background 样式（当前页实心主色） | EP Pagination 背景样式（不是 border 样式）视觉更紧凑，适合稠密表格页。 |

### 6. 审批卡片（看板内）

| 原型上有什么 | 为什么这样设计？ |
|---|---|
| 卡片内容：标题 + 事由一行 + 发起人+时间一行 | 信息密度严格三层：**第一层识别是什么事、第二层判断复杂度、第三层看是谁什么时候提的**。不塞更多字段——塞了也不会读，反而拉高卡片高度导致列内能显示的卡片变少。 |
| 紧急项右上角"紧急"红标、超时项底部橙色提示条 | 紧急和超时放不同位置不同颜色，因为**语义层级不同**：紧急是"发起人标为高优先级"（属于输入信息），超时是"系统计算出超时风险"（属于系统信号）。放一起会混淆，用户第一眼扫卡片时需要区分"这人自己喊急"和"系统判风险"。 |
| hover 卡片边框变主色 + 阴影加深 | 看板没有行高亮，卡片的 hover 是"我能点"的唯一视觉暗示。如果不加，用户可能以为卡片是纯展示。 |

### 7. 详情弹窗

| 原型上有什么 | 为什么这样设计？ |
|---|---|
| 640px 宽、max-h 85vh 的弹窗（不是抽屉，不是新页面） | 为什么选弹窗？三要素权衡：① 信息量——含申请表+时间线+意见框，需要 600px+ 宽；② 操作后上下文——处理完要**回到列表继续下一条**，抽屉会挤压列宽导致列表被遮挡一半，新页面则回跳重且丢失筛选/滚动位置。弹窗不遮挡列表视觉完整性且支持继续下一条。 |
| 弹窗头放标题+状态 Tag+紧急 Tag | 为什么状态不放正文里？弹窗头是**进入弹窗第一眼看的位置**，状态必须第一眼知道。正文里再放状态就是冗余。 |
| 申请信息区用两列网格（单号/类型/发起人/时间 4 项 2×2） | 表单类信息**左右两列是传统审批系统的常规做法**，用户不需要适应。金额、当前节点根据有无动态出现，避免空行。 |
| 审批轨迹用**时间线**（左竖线 + 节点圆点） | 流程的"顺序/完成度"用时间线比表格/文字描述直观 10 倍。节点颜色编码（绿=已通过/主色+环=当前/灰=待处理）让用户视线沿时间线扫一下就知道卡在哪。 |
| 当前节点圆点**有外环光晕**（ring-2 ring-primary/30） | 为什么当前节点视觉更重？因为详情打开的**首要目的是知道"该谁审了"**，比看历史更重要。外环让当前节点在时间线上像"灯塔"一眼找到。 |
| 意见输入框放在最底部、紧靠操作按钮 | 顺序符合行为流：**先看信息→看轨迹→写意见→点操作**。意见框放顶部会让用户先写意见（没看就写，决策质量差）。 |
| 驳回是红色 10% 背景、同意是实心主色 | **视觉权重排序**：同意（最高）> 驳回（次高，因为是反向动作要多确认一眼）> 取消（最低）。权重与操作的语义严重程度、使用频次匹配。 |
| 意见占位符写"请输入审批意见(可选)" | "可选"二字直接写进去，避免用户以为必须写而产生压力。同意可以不写意见，驳回建议写——这个规则没有在 UI 上强约束，是因为 MVP 阶段先保留灵活性。 |

### 8. Toast 反馈

| 原型上有什么 | 为什么这样设计？ |
|---|---|
| 操作后底部居中 Toast "已同意审批"，2.2s 自动消失 | 为什么不用弹窗"操作成功"让用户点确定？因为审批是**高频重复动作**，成功确认弹窗打断心流。Toast 足够——看一眼确认了，不用操作。2.2s 是行业经验值，够阅读不烦人。 |
| Toast 深底白字（反转色） | 页面主色是浅色底，反转 Toast 才不会和页面内容融在一起。 |

### 9. 空状态 / 加载状态

| 原型上有什么 | 为什么这样设计？ |
|---|---|
| 空状态：大号✓ + "暂无审批事项" + 辅助说明 | ✓ 不是"404"语义，是"**好事——你处理完了**"的正向暗示。配合辅助说明解释"为什么是空"，避免用户以为坏了。 |
| 加载态：4 行灰色脉冲骨架（animate-pulse） | 骨架屏比转圈加载指示器更好，因为它**保留布局预期**——用户知道"这里会出来列表而不是什么别的东西"，减少不确定感。 |

## Data Flow（数据从哪来 / 到哪去）

### 接口依赖（反向推导）

> 原型上显示了这些字段和聚合，意味着后端必须提供对应接口。这是反向 PRD 最有价值的部分——从 UI 反推数据契约。

| UI 模块 | 需要的后端接口 | 字段契约（从 UI 反推） |
|---|---|---|
| 统计卡片 4 数 + 趋势 | `GET /api/approval/stat?userId=xxx` | `{ pendingCount, timeoutCount, todayDone, weekDone, pendingTrend:[7], timeoutTrend:[7], todayTrend:[7], weekTrend:[7] }` |
| 审批列表（Tab 分类） | `GET /api/approval/list?userId=xxx&tab=todo&type=leave&status=pending&page=1&size=20` | `items: [{ id, title, type, applicant, submitTime, currentNode, status, urgent, timeout, amount, summary }]` |
| 详情弹窗 | `GET /api/approval/:id` | `{ 申请信息全字段, timeline: [{ node, approver, time, status, opinion }] }` |
| 审批操作 | `POST /api/approval/:id/action` | `body: { action: "approve"\|"reject", opinion }` |
| 批量同意 | `POST /api/approval/batch` | `body: { ids: [], action: "approve" }` → 建议返回 `{ successCount, failedCount, failedItems: [{id,reason}] }`（UI 目前只展示成功数，是 MVP 简化，生产建议做部分失败反馈） |

### 数据风险点（反向 PRD 必须追问的"坑"）

1. **聚合接口时效**：审批数据来自报销/请假/采购/用印 4 个业务系统。聚合接口是查缓存还是实时联调？实时联调 SLA 能否保证 ≤2s？如果某一业务系统挂了，聚合接口返回部分成功还是整体失败？UI 目前没有"部分加载失败"的降级展示，这是个风险。
2. **批量部分失败**：批量同意 10 条，有 3 条因为流程引擎状态已变而失败。UI 目前只 Toast "已批量同意 N 条"，没有告知失败。真实上线会让用户以为全成了。
3. **紧急/超时定义**：紧急是发起人手动勾选的，还是系统按类型默认？超时是按单流程节点的 SLA 算，还是按全流程总时长算？这两个规则没定义清楚，Tag 展示就没有可信度。
4. **审批权限**：谁能看到哪些审批？看板按类型分列时，会不会让用户看到自己不该看到的审批单号/发起人/金额摘要？UI 假设列表只返回有权限的，这是后端强依赖。

## Edge Cases（边界情况：原型没画的，但必须问清楚）

> 原型通常只画 Happy Path。反向 PRD 的价值就是把原型没画的场景一个个拎出来问。

| 边界场景 | 原型当前表现 | 必须追问的问题 |
|---|---|---|
| 某审批类型一列为 0 条 | 显示"暂无"文字占位 | 管理者关心"**为什么这类这个时间段是 0**"——是没申请，还是都批完了？是否需要区分"无待办"和"无任何"？ |
| 单列超过 50 张卡片 | 列内滚动 | 用户**不想滚动翻**，看板的"概览价值"就丧失了。是否需要 N 条以上时强制切换到列表？还是加"查看更多"？ |
| 紧急 + 超时同时出现 | 紧急标在右上，超时提示在底部（会同时出现） | 两个视觉信号叠加，卡片会变得很"重"。是否需要合并一个"紧急且超时"的超级标记？ |
| 详情弹窗打开，列表里同一条又被别人处理了 | 详情里的状态不会更新 | 状态冲突怎么办？用户点同意后系统返回什么 Toast？要不要在详情打开时做状态监听轮询？ |
| 同意按钮连点两次 | Toast 出现两次，实际请求可能发两次 | 按钮 loading 态（操作期间禁用）没做，后端幂等键没传。生产必须加。 |
| 批量选了已处理 + 未处理混合项 | UI 允许勾选任何行 | 批量同意时已处理项必然失败。是在批量前过滤掉，还是失败后告诉用户"有 N 条跳过"？ |
| 筛选结果为 0 | 用统一的"暂无审批事项"空状态 | 语义不准确——不是用户没事做，是筛选条件下没有。是否需要"重置筛选"快捷入口？ |
| 审批轨迹分支并行（复杂流程） | 原型只画了线性时间线 | 真实审批常有"会签/或签/并行分支"。线性时间线无法表达，后续需要换一种可视化（节点图 / 多层级时间线）。 |

## Error Handling（异常处理）

| 异常场景 | 原型当前表现 | 建议行为 |
|---|---|---|
| 列表接口失败 | 骨架屏消失后无反馈，空状态 | 应该 Toast "加载失败，请重试" + 局部重试按钮，不要让用户以为是空 |
| 详情接口失败 | 点开弹窗后内容空白 | 弹窗内应展示错误态，附带"重试加载详情" |
| 审批操作失败（权限不足 / 状态已变 / 网络） | 目前无处理逻辑 | Toast 明确说明失败原因："当前审批状态已变更，请刷新后重试" 而不是笼统的 "操作失败" |
| 统计接口失败（但列表接口成功） | 原型没做降级 | 卡片显示"—"和"加载失败"提示，列表照常工作，不要整体挂 |
| 批量操作网络超时 | 无处理 | 返回前禁用"批量同意"按钮，超时后 Toast "操作超时，请稍后查看状态"，不要让用户反复点。 |

## Design Intent 总结（从原型反推的核心设计决策）

1. **定位选择**：审批中心 = 管理视角优先，默认看板视图；执行视角补充，列表视图承载处理。
2. **颜色编码**：状态/类型/优先级全部用已验证的行业标准色，不发明新语义。
3. **渐进披露**：信息密度按"卡片概要→列表详情→弹窗全貌"三级递增，不一开始塞给用户所有字段。
4. **快捷 vs 安全的平衡**：行内操作有快捷，但视觉层级做低（淡色按钮），主路径仍是"看详情→写意见→决策"。
5. **MVP 减法原则**：筛选项只留 2 个高频维度、看板不加勾选、卡片不做二级菜单——减少第一次上手的心智负担。

## Future Extension（反向 PRD 必问：未来会加什么，原型要留扩展位）

1. **看板维度自定义**：现在按类型，未来可能按"按部门""按优先级""按当前节点负责人"分——列头要留维度切换的位置。
2. **转交 / 加签 / 委托**：详情弹窗底部现在只有 3 个按钮，未来加转交/加签/委托要预留操作区扩展性（或改为可折叠操作区）。
3. **审批模板配置**：这是另一个独立页面，不在本页做，但列表里"审批类型"要和模板管理做 ID 关联——不能硬编码类型名字。
4. **移动端**：当前布局（4 列看板）完全不适合移动端。未来做 H5 要单独适配，列表优先，看板降级为"类型筛选器"。
5. **审批 SLA 可视化**：超时现在只是文字标记。未来可能要在时间线的当前节点旁显示"剩余 XX 小时 / 已超时 XX 小时"的进度条。
6. **催办机制**：发起人视角下"我发起的"里，长时间卡在某节点，需要"催办"按钮——这会产生通知中心的联动，要提前规划消息通路。
7. **数据导出**：管理者需要导出本月审批明细做报表——列表顶部要留导入/导出按钮位置。
8. **看板拖拽流转**：原型上的看板是纯展示，未来要把看板做成"拖拽跨列=触发审批动作"（比如把请假卡拖到"已通过"列=直接同意），需要流程引擎支持+拖拽权限校验。

## 与正向 PRD 的差异（反推价值度量）

| 内容 | 正向 PRD（需求→方案） | 本反向 PRD（原型→意图） | 互补性 |
|---|---|---|---|
| 功能需求表 | 列出"要做什么" | 对每个模块追问"为什么这么设计" | ⭐ 反向补充了设计决策的理由 |
| 数据流 | 列出接口方向 | 反推出具体字段契约 + 聚合依赖 + 幂等风险 | ⭐⭐ 反向发现了 MVP 中没写的 4 个数据坑 |
| 边界情况 | 列了 5 条常见边界 | 列了 8 条 + 每个追问了"应该怎么办" | ⭐⭐ 反向发现 8 条中有 4 条正向没覆盖 |
| 异常处理 | 仅概括 | 列了 5 条具体场景 + 建议行为 | ⭐⭐⭐ 正向几乎没写异常，反向全部补齐 |
| 未来扩展 | 列了方向 | 具体到"当前 UI 上哪个区域要预留位" | ⭐⭐ 反向落地性更强 |

## Open Questions（反向 PRD 提给项目的待确认项）

> 反向 PRD 的最终产出不是"全知道了"，而是"挖出了这些需要进一步问的问题"。以下问题不回答，开发就会踩坑。

1. **紧急 / 超时的定义规则**是什么？谁有权标紧急？超时 SLA 按什么粒度算？
2. **行内直接同意**是否需要强制写意见？驳回是否要求必须写？
3. **批量同意**遇到部分失败时，UI 要反馈到单条级别，还是只 Toast 汇总？
4. **审批聚合接口**如果某子系统挂了，是降级返回"部分成功"（标注哪些类型不可用），还是整体报错？UI 上要怎么展示"部分加载"？
5. **看板列数量**如果超过 4 类（后续新业务线），是横向滚动还是折行？当前 4 类是硬编码的——要不要动态？
6. **详情弹窗**状态与列表不同步的问题，是否允许乐观更新（操作后直接从列表移除，不等到后端刷新）？
7. **权限模型**：谁能看到全量审批流水（管理员视角）？当前 UI 只有"个人视角"Tab，管理员视角是否是本页的一部分还是独立页面？
